# Проект: торговые боты для 5-минутных рынков Polymarket

Этот файл Claude читает **автоматически в начале каждой сессии**. Всё, что
здесь написано, не нужно пересказывать заново.

## Что это за проект

Боты на Up/Down рынки Polymarket (5 и 15 минут, BTC/ETH/SOL/XRP). Раунд:
в начале фиксируется таргет (`openPrice`), в конце цена сравнивается с ним.
Выигравший шэр платит **ровно $1**, проигравший — $0. Цена шэра и есть
оценка вероятности.

## Устройство

```
dashboard.py       одно окно, 4 панели (панели 1-3 показывают, 4-я торгует)
├─ pm_view.py      зеркало Polymarket
├─ fast_monitor.py цена с 7 бирж, опережает Polymarket на ~300мс
├─ book_monitor.py книга заявок Up/Down
└─ jump_trader.py  ЕДИНСТВЕННЫЙ, кто торгует (flowbot/jump*.py)

replay.py     прогон записи через стратегию с любыми порогами
features.py   измерение предсказательной силы признаков (IC)
scan.py       три счётчика по записи: арбитраж / премия за определённость / лаг
backtest.py   бэктест СТАРОЙ стратегии по историческому API
```

**Три режима входа** (`JUMP_ENTRY_MODE`, флаг `--entry-mode`). Отличаются
ровно поводом войти; ставка, лестница, фиксация и потолки общие. Разные
замки и разные файлы — запускаются одновременно, в том числе рядом с уже
работающей копией.

* `jump` (деф.) — скачок цены. Прежнее поведение, байт в байт.
* `edge` — `Φ(z) − ask ≥ JUMP_MIN_EDGE_CENTS`, лучшая из двух сторон.
* `lag` — `Φ(z нашей) − Φ(z по pm) ≥ JUMP_LAG_MIN_CENTS` И запас.

Настройки — `flow_jump.env` (в .gitignore). Правила — `JUMP.md`.
Тесты: `python -m pytest tests/ -q` (сейчас 307).

## Ключевая математика

```
P(Up) = Φ( (цена − таргет) / (σ · √время) )
```

Из неё следует всё остальное:

* **Чувствительность** процента к движению цены = `φ(z)/(σ√t)`. Максимальна
  на таргете, падает экспоненциально с расстоянием. Поэтому далеко от
  таргета проценты не реагируют на скачки — раунд уже решён.
* **«Далеко» измеряется в σ√t, а не в долларах.** 3σ это $38 при тихом
  рынке и $255 при разогнанном. Любой фиксированный долларовый порог неверен.
* **Нужный скачок линеен по σ.** Тот же эффект: $4 при σ=0.9, $28 при σ=6.
* **EV покупки при удержании до расчёта = `p − ask`.** Ровно это считает
  `JUMP_MIN_EDGE_CENTS`.

## Что уже выяснено (не переоткрывать)

* **Спред 5 центов, не 1.** Up 0.89/0.94 и Down 0.06/0.11 в сумме дают 1.00
  с обеих сторон — это ОДНА книга, показанная с двух сторон. «Купить Up по
  0.94» и «продать Down по 0.06» — одна заявка.
* **Разворот ПРОДАЁТ провалившуюся ногу** (а не держит её). Это и делает
  лестницу конечной: продажа возвращает капитал, в долге остаётся только
  реализованный убыток. Долг 1.00 -> 0.45 -> 0.29 -> 0.24 (сходится) вместо
  1.00 -> 2.50 -> 5.50 -> 11.50 (взрыв). Поэтому `JUMP_MAX_LADDER_LEGS=0`
  (без предела) безопасен. Открыта всегда ровно ОДНА нога.
* **Порог разворота считается от бида на входе**, не от уплаченного ask:
  спред 5¢ означает, что сразу после покупки бид на 5¢ ниже, и порог от ask
  срабатывал бы в тот же тик на каждой сделке.
* **Порог ВЗВОДА трейлинга — отдельная настройка** (`JUMP_TP_TRAIL_ARM`,
  деф. 2¢), и путать его с `JUMP_TP_TRAIL` нельзя. Когда взвод был привязан
  к `JUMP_TP_MIN_GAIN` (10¢), бид обязан был превысить УПЛАЧЕННЫЙ ask на 10¢
  (то есть 10¢ + весь спред от бида на входе) — до такого доживала едва ли
  каждая десятая нога, стоп молчал, и снаружи это выглядело как «трейлинг не
  работает». Два вопроса — «с какого момента защищаем» и «сколько разрешаем
  отдать» — должны настраиваться порознь.
* **`JUMP_STOP_LOSS` (деф. 1¢ от бида на входе) делает лестницу редкой**:
  он срабатывает раньше неё (2¢ + выдержка 0.6с). Это сознательный размен
  «выйти дёшево» против «отыграться разворотом»; вернуть лестницу — `=0`.
  Порядок проверок: фиксация прибыли → жёсткий стоп → лестница.
* **Округление шэров ВНИЗ опускало каждый ордер под доллар**: $1.00/0.53 =
  1.8867 → `floor2` → 1.88 → $0.9964. Теперь `ceil2` до `JUMP_MIN_ORDER_USDC`.
  Сравнивать надо НЕОКРУГЛЁННОЕ произведение: `round(0.9964, 2)` даёт ровно
  1.00, и проверка по округлённой сумме недобора не видит.
* **Достигнутую прибыль защищает ТОЛЬКО трейлинг-стоп** (`JUMP_TP_TRAIL`,
  деф. 2¢ от пика). Остальные четыре
  триггера на откате молчат по построению: `frozen` ждёт 8с застоя (процент
  падает за 2), `quiet` требует, чтобы замерла МОНЕТА, `faded` — чтобы монета
  развернулась. Плюс проверка «мы в плюсе» стоит перед ними, поэтому при
  истончении прибыли позицию переставало смотреть вообще. Боевой случай:
  вход 0.53, пик 0.70, выход −0.07. Трейлинг проверяется ПЕРВЫМ.
* **Исторические данные по СТАРОЙ лестнице** (когда ноги держались): ступени
  0-2 дали +$41, третья −$27.55. С продажей ноги эта арифметика уже другая —
  перемерить на новой записи.
* **σ в тихое воскресенье ~0.9 $/√с**, весь раунд решается в пределах ±$11
  от таргета. В рабочие дни в разы больше — пороги подстраиваются сами
  (`JUMP_ADAPTIVE`).
* **Опережение перед Polymarket ~288 мс** (видно в логе как `pm288`).
  Считать его надо от `fast_monitor.prices["polymarket"]`, а НЕ от таргета
  раунда — это разные вещи, и путаница здесь ломает любую модель.
* **Скачок как ТРИГГЕР неверен по построению.** Его нет ни в одном члене
  `EV = p − ask`. Он недостаточен (скачок $10 в 15σ от таргета не двигает
  процент) и не нужен (сигнал бывает без скачка: `σ√t` сжимается со временем,
  σ падает после всплеска, книга зевает после чужой сделки). Отсюда режимы
  `edge` и `lag`. Скачок остаётся признаком для `features.py`, не воротами.
* **Спред НЕ константа.** 5¢ при 0.89/0.94 около таргета, 1¢ при 0.97/0.98 на
  решённом раунде с глубиной 1500+. Значит `JUMP_MIN_EDGE_CENTS=3.0`,
  посчитанный как «половина спреда 5¢», местами завышен — мерить по записи.
* **`prices["polymarket"]` — это ЯКОРЬ УРОВНЯ в `fast_monitor`**: остальные
  биржи дебиасятся относительно него (`compute()`), поэтому в разрыве
  «наша цена − pm» нет постоянного базиса площадок. Это чистое опережение.
  Оговорка: pm сам входит в взвешенное среднее, поэтому разрыв слегка
  занижен — знак верен, величина консервативна.
* **DRY-RUN НЕ ПРОВЕРЯЕТ ПУТЬ ОРДЕРА.** Симулированный трейдер всегда
  отвечает `simulated_fill`, поэтому четыре дефекта жили только в бою:
  ответ биржи не разбирался вовсе (FAK может дать нулевой/частичный филл, а
  бот записывал ногу как полную); разворот покупал вторую сторону, даже если
  продать первую не удалось (открыты обе, долг посчитан от непроданной);
  продажа при пустой книге уходила по цене 0.00; пол цены продажи
  (`limit_price`) принимался и игнорировался. Разбор ответа — `flowbot/fills.py`,
  он честно помечает нераспознанное как UNKNOWN, а не угадывает.
* **РАЗМЕР ОРДЕРА — ТОЛЬКО ЦЕЛЫМИ ШЭРАМИ.** Polymarket отвергает покупку,
  если сумма в USDC (цена × размер) длиннее двух знаков: 0.57 × 1.76 =
  $1.0032 -> 400 `invalid amounts`. Цена всегда в целых центах, поэтому два
  знака гарантирует только целое число шэров. `floor2`/`ceil2` для размера
  покупки не годятся — `btc_bot.util.whole_shares`. Старый `presign_window`
  это знал (`int(trade_size/price)`), наш движок — нет, и первый же живой
  ордер упал. Тот же расчёт обязан быть в `replay.py`, иначе подбор порогов
  меряет не ту стратегию (есть тест на совпадение).
* **ПАУЗА ПОСЛЕ ОШИБКИ НЕ ДОЛЖНА ТРОГАТЬ ВЫХОД.** `JUMP_ERROR_COOLDOWN_S`
  блокировала любое действие, включая продажу: один отклонённый ордер — и
  бот 5 секунд даже не пытался выйти, пока цена падала. Вход откладывать
  можно, выход — никогда. Теперь пауза применяется только к ENTER/LADDER.
* **Разворот покупает вторую сторону ДАЖЕ ЕСЛИ продать первую не удалось**
  (осознанный выбор юзера). Плата: открыты обе ноги, долг посчитан как
  будто первую продали. Бот предупреждает в лог, но сделку не отменяет.
* **ПОЛ ЦЕНЫ ПРОДАЖИ ПРОТИВОРЕЧИТ СТОПУ.** `JUMP_MAX_SELL_SLIP` запрещал
  продавать, если бид ушёл ниже цены решения больше чем на порог. Но стоп
  существует ровно чтобы ВЫЙТИ на падении: чем быстрее рушится цена, тем
  упорнее бот держал ногу. В бою нога съехала с 0.47 до 0.10 при стопе,
  стоявшем на 0.45. Теперь по умолчанию **0** (выключен), продаём по
  текущему биду. Ненулевой имеет смысл только для фиксации прибыли.
* **Запись `--record` пишет ~10 ГБ в сутки** (68 МБ за 10 минут): такт
  случается на каждом событии книги, а не по таймеру. На VPS с 50 ГБ это
  четверо суток. Для суточного сбора надо либо прореживать, либо чистить.
* **МОЛЧАЛИВЫЙ ОТКАЗ ТОРГОВАТЬ — самый коварный отказ.** У запроса к бирже
  не было таймаута, поэтому один повисший ордер оставлял `busy=True` навсегда:
  строки состояния идут, решение «покупать» печатается на каждом такте, а
  сделок нет и причина нигде не названа. Теперь есть `FLOW_ORDER_TIMEOUT_S`
  (10с), сторож на залипший `busy` и лог `сигнал есть, но сделки нет: ...`.
  При таймауте нога НЕ записывается: неизвестно, дошёл ордер или нет, а
  фантомная позиция ломает и продажи, и долг лестницы.
* **После отказа биржи нужна ПАУЗА** (`JUMP_ERROR_COOLDOWN_S`, деф. 5с).
  Сигнал держится, пока держится рынок, поэтому отклонённый ордер иначе
  повторяется на каждом такте — десять раз в секунду.
* **Четыре изученных прибыльных кошелька — маркет-мейкеры**, не угадыватели
  направления: только BUY, обе стороны 50/50, пара Up+Down за $0.977 при
  выплате $1. Наш бот — их клиент: он переходит спред, они его собирают.

## Правила работы с этим проектом

1. **Не подбирать пороги на глаз.** Здесь уже дважды делались выводы на
   9-20 наблюдениях, и оба разворачивались от пары случаев. Есть `replay.py`
   и `features.py` — пользоваться ими.
2. **`--split` обязателен.** Признак, не переживший вторую половину выборки,
   был подгонкой.
3. **DRY_RUN=true по умолчанию.** Реальные деньги — только после сотен
   раундов на симуляции.
4. **Один бот на рынок И РЕЖИМ.** Вторая копия того же режима ведёт свою
   лестницу, риск складывается. Замок — `flowbot/singleton.py`, ключ
   `(монета, dry|live, режим входа)`; обойти можно только `--allow-multiple`.
   Разные режимы входа друг другу не мешают, это и есть способ сравнить их.
5. **Все `*.env` в .gitignore** — там поля PRIVATE_KEY/FUNDER. В репозитории
   только `flow_jump.env.example` с пустыми кредами.
6. Русские комментарии в коде — норма для этого проекта, продолжать так же.

## Текущее состояние и что дальше

Ветка: `claude/bot-crypto-setup-7amp2c`.

**Главное узкое место: нет данных.** Записи рынка (`--record`) ещё ни разу
не запускали, поэтому все настройки — догадки. Следующий шаг всегда один:

```
python dashboard.py --record market.jsonl              # сутки в dry-run (jump)
python jump_trader.py --entry-mode edge                # рядом, свой замок
python jump_trader.py --entry-mode lag                 # и ещё один

python scan.py market.jsonl                            # три счётчика
python features.py market.jsonl --split                # есть ли сигнал
python replay.py market.jsonl --sweep entry-mode jump edge lag
```

Записывать надо **одной** копией: рынок у всех один и тот же, три записи —
это только тройной расход диска. Сравнивать режимы честнее через `replay.py`
на одной записи, чем по трём живым запускам с разными потоками тиков.

Пока данных нет, любые новые модели и признаки строить преждевременно.
