# Скачковая система — 4-я панель дашборда

Первые три панели дашборда **показывают**. Четвёртая — **торгует**.
Она подключена к тем же трём источникам, что и остальные:

| Откуда | Что берёт | Модуль |
|---|---|---|
| 1. Цена (7 бирж + якорь Polymarket) | движение цены в **долларах** | `flowbot/signals.py::PriceEngine.swing` |
| 2. Книга Up/Down (поток CLOB) | «проценты» сторон, поток заявок | `flowbot/signals.py::BookEngine` |
| 3. Polymarket API | таргет раунда (`openPrice`) | `fast_monitor.official_target_task` |

Запуск отдельным окном:

```bash
cp flow_jump.env.example flow_jump.env   # один раз: свой пресет
python jump_trader.py                    # dry-run, BTC, ставка $1
python jump_trader.py --env-file flow_jump.env
python jump_trader.py --live             # РЕАЛЬНЫЕ ордера (нужны креды)
```

> Сам `flow_jump.env` в `.gitignore` (как и все `*.env` в проекте) — туда
> вписываются `PRIVATE_KEY`/`FUNDER`, и в git они попасть не должны. В репо
> лежит только `flow_jump.env.example` с пустыми кредами. На VPS:
> `chmod 600 flow_jump.env`.

В дашборде она поднимается сама:

```bash
python dashboard.py                      # 4 панели, торговля в dry-run
python dashboard.py --no-jump            # без неё, только три монитора
python dashboard.py --live --stake 2     # реальные деньги, ставка $2
```

## Четыре режима входа (`JUMP_ENTRY_MODE`)

Режимы различаются **ровно тем, что считают поводом войти**. Лестница,
фиксация и потолки у них общие — иначе сравнение мерило бы сразу
несколько изменений. Разные режимы = разные замки и разные файлы, поэтому их
держат запущенными **одновременно**, в том числе рядом с уже работающей копией.
(`impulse` вдобавок сам назначает ставку и потолок цены — это и есть его
предмет, см. ниже.)

| Режим | Триггер | Идея |
|---|---|---|
| `jump` (деф.) | скачок цены ≥ `$5·масштаб` | исходная: «цена дёрнулась — берём» |
| `edge` | `Φ(z) − ask ≥ JUMP_MIN_EDGE_CENTS` | то, что стоит в `EV = p − ask` |
| `lag` | `Φ(z нашей) − Φ(z по pm) ≥ JUMP_LAG_MIN_CENTS` **и** запас | книга считает по устаревшей цене |
| `impulse` | оценка качества `Q ≥ JUMP_IMP_MIN_SCORE` | «насколько хорош этот импульс», а не «далеко ли ушла цена» |

**Почему скачок как триггер неверен.** Его нет ни в одном члене `EV = p − ask`.
Отсюда обе беды сразу:

* **недостаточен** — скачок $10 в 15σ от таргета не двигает процент вообще
  (раунд решён), и вход туда съедается спредом;
* **не нужен** — сигнал бывает без всякого скачка: время идёт и `σ√t`
  сжимается, σ падает после всплеска, книга зевает после чужой крупной
  сделки. Каждый такой случай режим `jump` пропускает.

Режим `edge` эту дыру закрывает, но опирается на качество σ и на то, что
`Φ` верна. У краёв она врёт (у крипты хвосты толще нормальных), поэтому
`JUMP_MAX_LEG_PRICE=0.95` там не формальность, а единственная защита от
скупки всего по 0.96 «с запасом +4¢».

Режим `lag` строже: он требует и запас, и **названную причину** его
появления. Разрыв `наша цена − pm` — чистое опережение: в `fast_monitor`
цена Polymarket служит якорем уровня, относительно которого дебиасятся
остальные биржи, поэтому постоянного базиса между площадками в этой
разнице нет.

### Режим `impulse` — качество движения вместо его размера

Старый триггер задаёт один вопрос: «прошла ли цена достаточно долларов?».
Три совершенно разные ситуации отвечают на него одинаково:

| Что на самом деле | Старый триггер | Что надо было |
|---|---|---|
| $5 за 0.4с, цена держится | скачок $5 → **вход** | вход, и крупный |
| $5 за 15с плавным дрейфом | скачок $5 → **вход** | отказ: книга давно переоценила |
| $5 за 0.2с и сразу обратно | скачок $5 → **вход** | отказ: вынос ликвидности |

`flowbot/impulse.py` описывает движение **пятью** независимыми величинами и
не содержит ни одного порога:

| Величина | Что значит |
|---|---|
| `jump_usd` | знаковый ход от экстремума |
| `speed` | $/с за последнюю секунду |
| `accel` | текущая скорость ÷ средняя скорость самого импульса |
| `hold` | какую долю хода цена удержала |
| `age_s` | возраст экстремума |

### Решение — ОДНА оценка, а не восемь обязательных ворот

Так было до v23: каждый признак мог отменить сделку в одиночку. Провалил
один из восьми порогов — отказ, остальные признаки даже не считались.
На практике сильный сигнал пропадал из-за возраста импульса **8.2 секунды
вместо 8.0**: промах на два процента перечёркивал пять хороших признаков, и
сделок почти не стало.

Теперь каждый признак даёт оценку **0..1** по своей шкале
(`flowbot/score.py`), оценки складываются с весами, и решение принимается
**один раз**: `Score >= JUMP_IMP_MIN_SCORE` (0.70).

| Признак | Шкала (сокращённо) | Вес |
|---|---|---|
| скорость | 1.5σ/с → 1.0, 1.1σ/с → 0.8, 0.9σ/с → 0.6, <0.7σ/с → 0 | 0.40 |
| запас | 6¢ → 1.0, 4¢ → 0.8, 3¢ → 0.6, <2¢ → 0 | 0.30 |
| ход | 2.5σ → 1.0, 2.0σ → 0.8, 1.8σ → 0.6, <1.5σ → 0 | 0.20 |
| удержание | 95% → 1.0, 80% → 0.8, 70% → 0.6, <60% → 0 | 0.20 |
| возраст | ≤4с → 1.0, ≤8с → 0.7, ≤12с → 0.2, >12с → 0 | 0.10 |
| ускорение | 1.2 → 1.0, 0.8 → 0.7, 0.6 → 0.5, <0.4 → 0 | 0.10 |
| сдвиг % | 6¢ → 1.0, 3¢ → 0.8, 2¢ → 0.6, <1¢ → 0 | 0.10 |
| книга | перекос [−1..+1] → [0..1] | 0 |

Что это даёт на практике:

| Ситуация | Было | Стало |
|---|---|---|
| возраст 8.2с | отказ | Score 0.93 → **вход** |
| ускорение 0.45 | отказ | Score 0.91 → **вход** |
| ход 1.9σ | отказ | Score 0.90 → **вход** |
| три признака просели сразу | отказ | Score 0.76 → **вход** |
| удержание 55% (вынос) | отказ | Score 0.84 → **отказ** |
| ход 1.2σ (шум) | отказ | Score 0.81 → **отказ** |

### Ноль — это запрет, а не «слабо»

Последние две строки таблицы объясняют, почему в скоринге осталось одно
жёсткое правило. Вынос ликвидности набирает **0.84**, шум — **0.81**, и оба
спокойно прошли бы порог 0.70. Вес удержания (0.20 из 1.40) физически не
способен утопить сумму, если остальные признаки хороши.

Поэтому **ноль по любому признаку отменяет вход** (`JUMP_SCORE_VETO_ZERO`).
В шкалах ноль стоит там, где величина означает не «слабо», а «у нужного нам
сигнала так не бывает»: удержание ниже 60% — это разворот, а не откат; ход
меньше 1.5σ — это шум; скорость ниже 0.7σ — движение уже кончилось.

Всё, что **строго больше нуля**, не блокирует ничего и работает только
через вес — ровно так, как и задумывалось.

### Шкалы растягиваются настройками

Формы шкал сняты с прежних жёстких порогов, но сами эти опорные значения —
догадки. Настройки `JUMP_IMP_JUMP_SIGMAS`, `JUMP_IMP_SPEED_SIGMAS`,
`JUMP_IMP_MIN_HOLD`, `JUMP_IMP_MIN_ACCEL`, `JUMP_IMP_MAX_AGE_S` теперь
**растягивают** шкалу, а не режут по ней. Сохраняется форма («на пороге
0.6–0.8, заметно лучше — 1.0»), а ручка остаётся одна.

Отдельно так вернулся спред в расчёт запаса: абсолютная шкала «6¢ = отлично»
неверна там, где спред 10¢ — после круга от такого запаса не остаётся
ничего. Опорный порог = `max(JUMP_MIN_EDGE_CENTS, множитель × спред)`.

```bash
python replay.py market.jsonl --sweep score-min 0.60 0.65 0.70 0.75 0.80
python replay.py market.jsonl --sweep veto-zero true false
python replay.py market.jsonl --sweep w-speed 0.2 0.4 0.6
python stats.py --split s_age      # какой признак чаще тянет вниз
```

**Ставка ПЛОСКАЯ, $1 на любой сигнал** (`JUMP_STAKE_BY_QUALITY=false`):
разный размер позиции смешивает «сигнал был лучше» с «мы поставили больше»,
и разделить их в журнале потом нечем.

### Структура книги заявок

`flowbot/bookfeat.py` считает по каждой стороне: перекос глубины
(`imbalance`, [−1..+1]), долю крупнейшей заявки в ask (`wall` — стена на пути
движения), изменение глубины за окно (`ask_trend` — снимают ли ликвидность).

**Жёсткие ворота по книге выключены** (`JUMP_BOOK_MIN_IMBALANCE=0`,
`JUMP_BOOK_MAX_WALL=0`), и это не лень. Признаки уже пишутся в журнал каждой
сделки; включать их в отбор до того, как по журналу видно их влияние, —
ровно та ошибка, на которой проект обжигался дважды. Сначала измерить.

```bash
python stats.py --split book_imb
python replay.py market.jsonl --sweep book-imbalance 0 0.1 0.2 0.3
```

```bash
python jump_trader.py --entry-mode edge     # рядом с уже работающим jump
python jump_trader.py --entry-mode lag
python jump_trader.py --entry-mode impulse
python replay.py market.jsonl --sweep entry-mode jump edge lag impulse
```

Сравнивать режимы честнее **на одной записи** через `replay.py`: там рынок
буквально один и тот же. У живых запусков у каждого свой поток тиков.

## Правила сделок

### Как ловим движение (`JUMP_TRIGGER_MODE`, только режим `jump`)

По умолчанию — **`swing`**: система непрерывно держит локальное **дно и пик**
цены за последние `JUMP_SWING_LOOKBACK_S` секунд (деф. 60) и меряет, насколько
цена от них ушла. Как только движение от экстремума перевалило порог —
покупка **в тот же тик**, сколько бы времени движение ни заняло. Ждать нечего:
проверка идёт на каждом обновлении книги, а не по таймеру.

Альтернатива — `window`: сравнить цену сейчас и `JUMP_WINDOW_S` секунд назад.
Так было раньше; режим оставлен, но у него два изъяна:

| Что произошло | `window` 3с | `swing` |
|---|---|---|
| рост $12, растянут на 10 секунд | **+$3.60** → порога нет, сделки нет | **+$12.00** → вход |
| скачок $6 за 0.6 секунды | **+$4.50** → порога нет, сделки нет | **+$6.00** → вход |
| выброс на $20 и обратно | +$0.00 | +$1.00 — отфильтрован |

Второй случай особенно неприятен: окно занижает даже **быстрый** скачок,
потому что концы окна берутся медианой узких подокон, и часть движения
срезается. Порог $5 при этом не срабатывает, хотя цена реально прыгнула на $6.

Защита от ложных срабатываний в режиме `swing`: дно и пик записываются по
**медиане трёх** последних цен, поэтому одиночный выброс консенсуса не может
«нарисовать» новое дно. Текущая цена при этом берётся **сырой** — медиана
отстаёт на тик, а весь смысл режима в мгновенной реакции. От выброса в самой
свежей цене защищает отсев в консенсусе `fast_monitor`: источник, ушедший от
медианы семи бирж дальше 25 б.п., в цену вообще не попадает.

После сделки и на границе раунда экстремум **переставляется** на текущую цену
— иначе то же самое дно секунду спустя открыло бы вторую такую же позицию.
Это и есть защита от повтора; таймер `JUMP_REENTRY_COOLDOWN_S` теперь **0**.

> Пауза в секунду останавливала не «вторую позицию на том же движении» (её
> уже держит сброс экстремума), а **лестницу**: на активном рынке нога
> успевает провалиться быстрее, чем пауза истечёт, и разворот просто не
> случался. Ненулевое значение осталось для отладки.

### Вход

Покупаем ту сторону, **куда** пошла цена (вверх → `Up`, вниз → `Down`).

| Процент этой стороны | Нужен скачок | Доп. условие | Дорожка |
|---|---|---|---|
| **≥ 51¢** (дорогая) | **$5** | — | **A** |
| **< 51¢** (дешёвая) | **$15** | цена не дальше **$100** от таргета | **B** |

Смысл: если рынок уже согласен с направлением (сторона стоит дороже 51¢),
хватает малого толчка. Если мы идём против мнения рынка (сторона дешёвая),
требуем и толчок втрое сильнее, и чтобы раунд ещё реально можно было
перевернуть — то есть цена рядом с таргетом.

«Процент» на входе читается по **ask** (это то, что мы реально платим),
на выходе — по **bid** (это то, за что реально можем продать). Ровно 0.51
считается дорогой стороной.

### Разворот: закрываем ногу, обратную сторону покупаем ЗАНОВО

`JUMP_LADDER_REENTERS=true` (по умолчанию).

Старая лестница молча принимала допущение, которое почти никогда не верно:
**убыток по одной стороне — подтверждение другой.** Но рынок мог просто
встать. Тогда плохи обе стороны, а автоматический переворот лишь удваивает
число сделок и риск.

Теперь последовательность такая:

1. процент ноги упал на `JUMP_LADDER_LOSS` ниже бида на входе и продержался
   `JUMP_LADDER_GRACE_S` — **закрываем ногу**, и на этом действие кончается;
2. обратная сторона проходит **все ворота стратегии заново**, как обычная
   новая сделка: ход в σ, скорость, удержание, ускорение, возраст импульса,
   расстояние до таргета, запас, потолок цены;
3. планка качества для такого входа **выше обычной** — `JUMP_LADDER_MIN_Q`
   (1.5 против 1.0) в течение `JUMP_LADDER_STRICT_S` секунд (30). Переворот
   рискованнее первого входа, значит сигнал обязан быть сильнее среднего;
4. не прошла — **остаёмся без позиции** и ждём сигнала.

Побочный, но важный эффект: разворот стал **продажей**. Продать можно всегда
— пауза после отказа биржи держит только покупки, — поэтому дыра «разворот
отложен, стоп молчит, нога висит» здесь закрыта по построению.

Старый переворот никуда не делся: `JUMP_LADDER_REENTERS=false`. Сравнить их
честно можно только на записи:

```bash
python replay.py market.jsonl --sweep ladder-reenters true false
python replay.py market.jsonl --sweep ladder-min-q 1.0 1.25 1.5 2.0
```

### Старый разворот (`JUMP_LADDER_REENTERS=false`)

Как только процент купленной стороны пошёл **против нас** (ниже бида на
входе на `JUMP_LADDER_LOSS`), бот **продаёт эту ногу** и сразу берёт
противоположную в таком размере, чтобы перекрыть убыток и выйти в плюс:

```
шэров = (вложено за раунд + желаемый плюс) / (1 − цена входа)
```

и так по кругу. Открытой всегда остаётся **ровно одна нога**.

**Почему продажа старой ноги — не деталь, а главное.** Она возвращает
капитал, поэтому в долге остаётся только реализованный убыток (спред плюс
просадка), а не вся стоимость ноги:

| ступень | держим старую | продаём старую |
|---|---|---|
| 0 | $1.00 | $1.00 |
| 1 | $2.50 | **$0.45** |
| 2 | $5.50 | **$0.29** |
| 3 | $11.50 | **$0.24** |
| 4 | $23.50 | **$0.22** |

Долг **сходится** вместо удвоения. Именно поэтому предел ступеней здесь не
нужен: `JUMP_MAX_LADDER_LEGS=0` (без ограничений) безопасен.

**Что значит «пошло против»**: бид упал ниже **бида на момент входа** на
`JUMP_LADDER_LOSS` (деф. 2¢) и продержался так `JUMP_LADDER_GRACE_S` (деф.
0.6с). Отсчёт именно от бида, а не от уплаченного ask: спред 5¢ означает, что
сразу после покупки бид на 5¢ ниже цены покупки, и порог от ask срабатывал бы
в тот же тик на каждой сделке.

### Фиксация прибыли — обе дорожки

#### Выход 1: трейлинг-стоп (`JUMP_TP_TRAIL`, деф. 2¢)

Как только нога **хоть раз** стоила на `JUMP_TP_TRAIL_ARM` (деф. 2¢) дороже
уплаченного ask, под пиком встаёт стоп: бид упал на `JUMP_TP_TRAIL` ниже
максимума — продаём, и никакие другие условия не нужны.

> **Порог взвода — не мелочь, а то самое место, где трейлинг ломался.**
> Сначала взвод был привязан к `JUMP_TP_MIN_GAIN` (10¢). Это означало «бид
> обязан превысить УПЛАЧЕННЫЙ ask на 10¢», то есть подняться на 10¢ плюс
> весь спред от бида на входе. Почти ни одна нога до такой планки не
> доживала: стоп просто не включался, позиция падала от пика на сколько
> угодно, и снаружи это выглядело как «трейлинг не работает». Отдельный
> `JUMP_TP_TRAIL_ARM` разводит два разных вопроса — «с какого момента
> защищаем» и «сколько разрешаем отдать».

Это единственная защита достигнутой прибыли, и раньше её не было вовсе.
Реальный случай из боя: вход **0.53**, пик **0.70** (+17¢), выход **−7¢**
через лестницу. Ни один из четырёх триггеров ниже на откате не сработал:

| Триггер | Почему промолчал |
|---|---|
| `deadline` | до конца раунда 200с |
| `frozen` | ждёт 8с застоя, а процент падал за 2 |
| `quiet` | требует, чтобы замерла **монета**, а она двигалась |
| `faded` | требует, чтобы монета ещё и **развернулась** |

И главное: проверка «мы в плюсе» стояла **перед** всеми четырьмя, поэтому
как только прибыль истончалась ниже 10¢, позицию переставало смотреть
вообще — ровно тогда, когда защищать её нужнее всего. Трейлинг проверяется
**до** этой проверки.

Оба порога — предположения, а не измерения:

```bash
python replay.py market.jsonl --sweep trail 0.01 0.02 0.03 0.05
python replay.py market.jsonl --sweep trail-arm 0.01 0.02 0.05 0.10
```

#### Выход 2: жёсткий стоп (`JUMP_STOP_LOSS`, деф. 1¢)

Бид ушёл ниже **бида на входе** на `JUMP_STOP_LOSS` — выходим сразу, без
выдержки и без разворота.

Отсчёт от бида на входе, а не от уплаченного ask, по той же причине, что и
у лестницы: спред означает, что сразу после покупки бид уже ниже ask (при
спреде 3¢ — на все три). Стоп «на цент ниже входа», отсчитанный от ask,
сработал бы в тот же тик на **каждой** сделке и превратил бы бота в машину
по выплате спреда.

#### Кто главнее — разворот или стоп (`JUMP_LADDER_BEFORE_STOP`, деф. `true`)

Порядок проверок: **фиксация прибыли → лестница → жёсткий стоп.**

**Поменять местами вызовы было бы недостаточно.** Порог стопа (1¢) *меньше*
порога лестницы (2¢ плюс `JUMP_LADDER_GRACE_S`), поэтому по цене стоп
наступает раньше при любой очерёдности: бид проходит отметку −1¢ до того, как
доберётся до −2¢. Приоритет означает буквально другое — **пока ногу способен
взять разворот, стоп её не трогает** (`JumpStrategy._ladder_blocked`).

Стоп при этом не исчез, а стал **страховкой**. Он срабатывает ровно тогда,
когда развернуться не во что:

| Почему разворот невозможен | Что делает стоп |
|---|---|
| `JUMP_LADDER_ENABLED=false` | работает как раньше |
| упёрлись в `JUMP_MAX_LADDER_LEGS` | работает как раньше |
| у обратной стороны нет `ask` | работает как раньше |
| обратная сторона дороже `JUMP_MAX_LEG_PRICE` | работает как раньше |
| расчёт шэров дал 0 | работает как раньше |
| идёт пауза после отказа биржи | работает как раньше |

> Последняя строка — дыра, которую этот приоритет чуть не открыл. Движок
> придерживает **входы и добор** после отказа биржи (`JUMP_ERROR_COOLDOWN_S`),
> но не продажи. Разворот — это покупка, значит на паузе он не пройдёт. Если
> бы стоп продолжал считать «ногу возьмёт разворот», нога висела бы без
> выхода все пять секунд — ровно тогда, когда цена падает. Поэтому снимок
> несёт флаг `entries_paused`, и стоп на паузе возвращается к работе.

**Плата названа честно:** между 1¢ и 2¢ нога больше не режется, и в течение
выдержки 0.6с падение может уйти дальше. Это размен «выйти дёшево» против
«отыграться разворотом», и он сдвинут в сторону разворота. Какая сторона
выгоднее — **неизвестно**, пока нет записи рынка:

```bash
python replay.py market.jsonl --sweep ladder-first true false
```

**Стоп подстраивается под волатильность** (`JUMP_STOP_ADAPTIVE`, по умолчанию
включён): 1¢ — это порог, снятый при σ≈0.9; при σ=4 такое колебание
происходит само по себе несколько раз в секунду, и стоп режет живые позиции
шумом. Правило то же, что у порогов входа:

```
стоп = ограничить(JUMP_STOP_LOSS · σ/JUMP_SIGMA_REF, JUMP_STOP_LOSS, JUMP_STOP_MAX)
```

#### Выход 3: смерть скорости (`JUMP_EXIT_SPEED_DROP`, деф. 0.7)

Скорость монеты упала более чем на 70% от пиковой скорости, зафиксированной
за время жизни ноги — выходим, **не дожидаясь отката цены**.

Трейлинг ждёт, пока бид отдаст 2¢; к этому моменту книга уже всё поняла и
эти 2¢ отданы. Здесь смотрим не на книгу, а на **монету**: движение, которое
нас завело, кончилось — повода держать больше нет, независимо от того,
успел ли откатиться процент.

Порог не применяется к слабым импульсам: падение с 0.2 $/с до 0.05 $/с — это
тоже «−75%», но там и падать было нечему. Пиковая скорость ноги должна быть
хотя бы `JUMP_EXIT_SPEED_FLOOR` (деф. 2) σ в секунду.

#### Остальные выходы

Работают как более ранние: продаём, если мы **в плюсе** минимум на
`JUMP_TP_MIN_GAIN` (деф. 10¢) **и** сработало хотя бы одно:

* **проценты перестали подниматься** — пик не обновлялся `JUMP_TP_STALL_S`
  секунд (деф. 8);
* **цена монеты замерла** — движение не больше `JUMP_TP_QUIET_USD` (деф. $1.5);
* рост кончился: скачок больше не идёт в нашу сторону **и** (процент откатился
  от пика, либо поток заявок развернулся против нас);
* до конца окна ≤ `JUMP_TP_DEADLINE_S` (деф. 5с).

Это закрывает случай **«вышли в хороший плюс, досидели до расчёта и ушли в
минус»**: как только рост встал, прибыль забирается, а не проверяется на
прочность оставшимися минутами раунда. После выхода бот сразу свободен искать
следующий вход — **ограничения «одна сделка в раунде» нет**.

## ⚠️ Что всё ещё стоит проверить до `--live`

Разворот с продажей старой ноги убрал экспоненциальный рост долга, но не
сделал стратегию бесплатной. Каждый разворот стоит **спред плюс просадку**:
вошли по 0.50 (бид 0.45), вышли по 0.40 → потеряли 10¢ на ноге. Если цену
мотает часто, эти 10¢ платятся снова и снова, и никакой добор их не вернёт —
он лишь не даёт долгу расти лавиной.

Остались предохранители:

| Предохранитель | Деф. | Что делает |
|---|---|---|
| `JUMP_MAX_LADDER_LEGS` | **0** | без предела (безопасно, т.к. долг сходится) |
| `JUMP_MAX_ROUND_USDC` | 25 | потолок всех вложений в один раунд |
| `JUMP_MAX_LEG_PRICE` | 0.95 | дороже не разворачиваемся: шэров нужно слишком много |

Потолок раунда проверяется **дважды** — в стратегии и ещё раз перед самой
отправкой ордера, потому что за время пинга цена филла успевает вырасти.

Прогони `python replay.py market.jsonl --sweep profit 0.25 0.5 1.0` на записи,
прежде чем идти в `--live`.

## Счётчики по записи (`scan.py`)

Три вопроса, на которые нельзя ответить рассуждением, но можно — записью.
Ничего нового записывать не надо: всё уже пишется.

```bash
python scan.py market.jsonl              # все три
python scan.py market.jsonl --certain --floor 0.97 --tail 30
python scan.py market.jsonl --lag --split
```

1. **Арбитраж.** Как часто `ask(Up) + ask(Down) < $1.00` — пара дешевле
   гарантированной выплаты. Считается с учётом объёма верхнего уровня:
   прибыль ограничена тем, что реально можно взять, а не тем, что хочется.
2. **Премия за определённость.** За 30с до конца сторона стоит 0.98, а
   ценового риска уже нет — это +2% против риска *операционного*. Берётся
   **одно наблюдение на раунд** (соседние такты не независимы), и при нуле
   проигрышей печатается верхняя граница частоты сбоя по правилу трёх:
   ноль на 288 раундах означает «реже чем ~1%», а не «никогда». Для ставки
   98:2 нужна точность до сотых процента, то есть тысячи раундов.
3. **Лаг.** Распределение `наша цена − pm` и его IC против будущего движения
   середины книги, с проверкой на второй половине выборки.

## Чем живая торговля отличается от dry-run

Симулированный трейдер всегда отвечает `simulated_fill`, поэтому целый пласт
кода до первого `--live` не выполнялся ни разу. Там нашлось четыре дефекта:

| Что было | Чем грозило |
|---|---|
| ответ биржи не разбирался вовсе | ордер уходит как **FAK**: несведённый остаток отменяется. Филл мог быть нулевым, а бот записывал ногу как полную — дальше «продавал» несуществующие шэры и вёл лестницу от выдуманного долга |
| разворот покупал вторую сторону, даже если продать первую не удалось | открыты **обе** ноги, чего конструкция не допускает, и долг посчитан от ноги, которая осталась у нас |
| продажа при пустой книге уходила по цене **0.00** | шэры отдавались даром |
| пол цены продажи принимался и **игнорировался** | на обвале книги нога продавалась по любой цене, какую та покажет |

Разбор ответа — `flowbot/fills.py`. Он различает три исхода:

* **REJECTED** — биржа явно отказала (`errorMsg`, `success: false`,
  `status: unmatched`). Ногу **не открываем**.
* **FILLED** — подтверждено. Если пришёл объём и он меньше запрошенного,
  учитываем **фактический**, а остаток ноги живёт дальше
  (`record_partial_sell`).
* **UNKNOWN** — схему ответа не распознали. Считаем исполненным, но пишем
  в лог полный ответ и требуем сверить позицию на сайте.

Последнее — сознательная честность: точная схема ответа CLOB здесь не
проверялась и зависит от версии клиента. Лучше сказать «не знаю» и показать
сырой ответ, чем угадать и молча разойтись с биржей.

`JUMP_MAX_SELL_SLIP` — пол цены продажи, **по умолчанию 0 (выключен)**.

Идея была защитить от обвала книги, но она противоречит смыслу стопа: стоп
нужен, чтобы **выйти** на падении, а пол запрещает продавать именно тогда,
когда падает сильнее всего. Чем быстрее рушится цена, тем упорнее бот держал
бы ногу. В бою это дало съезд с 0.47 до 0.10 при стопе, стоявшем на 0.45.

Ненулевое значение осмысленно только для фиксации прибыли, где ждать
действительно можно. Для стопа — никогда.

## Одна копия на рынок

Запустить **тот же режим** дважды на одной монете нельзя — вторая копия
откажется стартовать:

```
ERROR  Скачковая система для BTC (dry) уже запущена (PID 5965). Вторая копия
       вела бы свою лестницу — риск сложился бы, а потолок $25 за раунд
       превратился бы в $50.
```

Это не придирка: каждая копия ведёт **свою** лестницу и про чужие не знает.
Три копии = тройной риск при тех же настройках, а в `jump_trades.csv`
переплетаются три независимые цепочки `cumulative_pnl`, по которым уже не
разобрать, что происходило. Признак того, что копий несколько — одна и та же
нога (`A0 Up`, тот же вход, та же цена) повторяется в раунде 2-3 раза.

Разные монеты, разные режимы исполнения (`dry` / `live`) и **разные режимы
входа** (`jump` / `edge` / `lag`) — разные замки, они друг другу не мешают.
Осознанно нужно несколько копий одного режима — флаг `--allow-multiple`.

Файлы тоже разведены автоматически: `edge` пишет в `jump_trades_edge.csv` и
`market_edge.jsonl`, `lag` — в `*_lag.*`. Режим `jump` сохраняет прежние
имена, чтобы уже запущенная копия не потеряла свою историю.

## Что видно в логе

Раз в секунду — строка состояния:

```
t-176s | BTC 65,054 цель 65,107 | скачок +6.40$/3с | Up 0.34/0.35 Down 0.65/0.66
        | поз A0:Up@0.60×1.7 | вложено $1.00 | $99.00 | держу до расчёта
```

Сделки печатаются отдельно и пишутся в `jump_trades.csv`:

```
>>> ENTER:  СКАЧОК $+8.00 за 3с (вверх) → Up @ 0.60 [дорожка A: порог $5], ставка $1.00
КУПЛЕНО [A#0] Up — 1.66 шэр @ $0.60 (=$1.00) | вложено за раунд $1.00
>>> LADDER: ЛЕСТНИЦА #1: Up упал до 0.40 (вход 0.60) → беру Down 3.75 шэр @ 0.60
            = $2.25, чтобы перекрыть $1.00 и выйти +$0.50
СЕТТЛ (окно закончилось) [A#1] Down ВЫИГРЫШ — payout $3.75 | P&L +1.50
── раунд закрыт: ног 2, выплата $3.75, P&L раунда +0.50 ──
```

В поле `outcome` CSV пишется дорожка и номер ноги (`A0 Up`, `B1 Down`) —
видно, какая ветка логики её открыла.

## Архитектура

```
flowbot/
  jump.py          ЧИСТАЯ логика: вход / лестница / фиксация (юнит-тесты)
  jump_engine.py   движок: фиды + книга + таргет + трейдер, много ног сразу
  jump_run.py      CLI
  config.py        пороги (JUMP_*) + validate_jump()
  signals.py       PriceEngine.move_usd() — скачок в долларах
jump_trader.py     обёртка запуска из корня
flow_jump.env      пресет
tests/
  test_jump_strategy.py   31 тест чистой логики (без сети)
  test_jump_engine.py     11 оффлайн-тестов движка (покупка/добор/расчёт)
```

`jump_engine.JumpEngine` наследует `flowbot.engine.FlowEngine`, поэтому весь
транспорт (поток книги, замер пинга, баланс, CSV) переиспользован как есть.
Отличие — позиция не одна: после добора мы держим обе стороны сразу, поэтому
переопределены учёт позиции, исполнение и расчёт в конце окна.

Тесты:

```bash
python -m pytest tests/test_jump_strategy.py tests/test_jump_engine.py -q
```
